## 🚨 本番公開の前に（コードだけでは終わらない作業）

環境を触る作業は [`../SETUP.md`](../SETUP.md) に手順と実際の値（DNS レコード、
Webhook id、ドメイン）をまとめてある。要点だけ再掲する。

1. **`feat/integrate-admin-dashboard-catalog` を main へマージする** — 本番 Worker は
   いまだに `feat/admin-products-inventory`（未マージ）で動いている。main だけを
   デプロイすると商品管理画面と在庫上限が消える。
2. **本番 D1 に `0007`〜`0013` を適用する** — 7 本未適用。`0012` が旧 `product_sku` を
   `inventory` + `product_price` へ移す。
3. **`ADMIN_EMAILS` を設定する** — ソースのフォールバック owner を撤去したので**必須**。
   未設定だと誰も `/admin` に入れない。
4. **Stripe Webhook に `charge.refunded` と `charge.dispute.created` を足す** — 現在 4 件。
5. **Resend のドメイン認証と `RESEND_FROM`** — 未認証のあいだ、確認メールは
   アカウント所有者にしか届かない＝誰も会員登録を完了できない。
6. **通信販売酒類小売業免許の番号を入れる** — `src/data/fujisan-legal.ts` の
   `LIQUOR_LICENCE`。未設定のあいだ `npm run deploy` は predeploy で止まる。
   **それらしい伏せ字で埋めないこと**（本物に見えたまま公開される）。
7. **実在庫を入れる** — 本番は全 SKU 一律 24 本の暫定値。`/admin/products` で差し替える。

### 既存の法人アカウントを承認する

取扱店の承認フローを入れたため、**`trade_account` に行が無い法人は未承認**として扱われ、
卸価格が表示されない。この機能より前に登録したお客様がいる場合は
`/admin/customers` で「未申請（旧アカウント）」と表示されるので、確認のうえ承認すること。

### 決めれば埋まるもの

- **SNS アカウント** — `FujisanFooter.tsx` の `SOCIAL_LINKS`（空なら非表示）
- **適格請求書（インボイス）登録番号** — `INVOICE_REGISTRATION_NUMBER`。未登録なら `null` のまま
- **独自ドメイン** — `NEXT_PUBLIC_SITE_URL`（canonical / OGP / sitemap の基底。ビルド時に確定）

## 積み残し

優先度順。着手時はこのファイルを更新すること。

### BtoB の発注機能

承認フローと卸価格の表示は実装済み。残るのは**発注そのもの**で、`/shop/business` は
いまも卸価格表の閲覧までしかできない。ここから先は決済条件の判断が要るため保留。

- 法人向けカート（ケース単位・卸価格）
- 銀行振込／掛売の決済分岐（現状はカードのみ）— **与信の運用と、オフライン入金の
  消し込みを誰がどう行うかを決めないと設計できない**

### 商品カタログ

価格と在庫は D1 へ移したが、**銘柄そのものの追加・文言・画像の変更は引き続きデプロイが必要**
（`src/data/fujisan-products.ts`）。ストーリーや写真は運用で日々変わる値ではないため、
いまのところこれで困っていない。

- 入荷予定・ロット・賞味期限の管理は無い
- 在庫切れ間近のメール通知は無い（`/admin` のアラートを見に行く必要がある）
- 商品ページは静的書き出しなので、残数そのものは出していない。価格と完売は
  `/api/catalog` からハイドレーション後に反映する

### 管理ダッシュボードの続き

`/admin` に売上（今日・今月・累計）、要対応の件数、在庫アラート、直近の注文を出した。
まだ無いもの：

- 期間を指定した絞り込み・グラフ
- CSV エクスポート
- 納品書・送り状の印刷
- 個人顧客の一覧（`/admin/customers` は取扱店のみ）

### チーム招待の一覧

招待に 14 日の期限を入れたが、`/admin/team` は**登録済みメンバーしか表示しない**。
「誰を招待中か」「その招待が失効していないか」が画面から分からないので、
招待し直すべきかを判断できない。`team_invite` を一覧に出すのが次の一手。

### 領収書の宛名変更

いまは登録名で固定。法人利用で「上様」や部署名を入れたい要望が出たら対応する。

## 技術的負債

### ~~`drizzle/` の journal がずれている~~（解消済み）

`0006` 以降が手書き追加で `meta/_journal.json` に載っておらず、`drizzle-kit generate`
を実行すると適用済みの列を二重に出力する状態だった。journal を SQL 15 本と
1 対 1 に揃え、現在のスキーマを `0014_snapshot.json` として置き直した。
`drizzle-kit generate` は「No schema changes」を返す。

`0006`〜`0013` の**中間スナップショットは無い**（当時の状態を復元できないため）。
`generate` は最後のスナップショットしか読まないので支障はないが、
`drizzle-kit up` / `drop` は使わないこと。

同じズレが再発しないよう `src/db/__tests__/migrations.test.ts` が見張っている
（SQL を頭から流して DB を作れること・journal が実ファイルと対応すること）。

### マイグレーション番号が一度衝突した

`0007` が 2 系統に存在した（`0007_product_sku.sql` と `0007_contact_message.sql`）。
ブランチを分けたまま両方でマイグレーションを足したため。ファイル名が違うので
`d1 migrations apply` は両方とも適用してしまい、**使われない表が本番に残る**。
`0012` で片付けたが、長生きするブランチでスキーマを触るときは番号を先に予約すること。

### 日付フォーマット

Workers は UTC で動く。日付を出すときは必ず `src/lib/format-date.ts` のヘルパーを使うこと
（`timeZone: "Asia/Tokyo"` を省くと JST 00:00〜09:00 の出来事が前日の日付になる）。
期間で集計するときは `jstDayStart` / `jstMonthStart` を使う。
ローカルの OS が JST だと気づけない種類のバグ。
